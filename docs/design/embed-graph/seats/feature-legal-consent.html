Full card — what & why, for whom, flows, is / is not

What & Why

Legal-consent is the data-rights spine (D148, labels L3-L6). The record (L4): ConsentRecord is append-only — every acceptance inserts a row (services/consent.py:30-37); "current" is the latest row and required means its policy_version differs from the server's CONSENT_POLICY_VERSION ("2026-07-14", constants.py:74). POST /consent stamps the SERVER's version, never the client's echo, so a stale client cannot record acceptance of a retired policy (api/consent.py:51-54); capture works pre-household by design (user-scoped, no require_household()). The documents (L3): Privacy + Terms live as typed content (features/legal/legalContent.ts) rendered at public routes outside the auth guards — readable before signup — and as in-content sheets inside setup and Settings so opening them never unmounts a half-filled wizard. The disclosures: the Fuentes de información Settings section pins the AI-assisted disclaimer (diet/allergen values are AI-generated, NOT medically verified — "Verifica siempre los ingredientes"), lists the curated never-AI safety sources (FDA, MINSAL, WHO, ACHIPIA), and offers the legal docs — the founder's stance that disclosure coexists with the R8 hard wall. The rights: GET /account/export streams every row the user owns as one downloadable gustify-datos.json — scope MIRRORS the deletion set (including the consent ledger itself) so what leaves equals what would be destroyed (account_export.py:1-7, :78-93). DELETE /me erases with ordering that routes around schema facts (account.py:47-100): authored recipes hard-deleted with children, no-FK tables swept explicitly, the household destroyed only if no other member remains, then the user-row cascade — commit FIRST, Firebase identity delete after, best-effort (auth's card owns that ordering). The web gate is type-to-confirm ("ELIMINAR"/"DELETE", exact and case-sensitive) with honest failure copy (accountDeletionModel.ts, C1502-C1512).

For Whom

  • Every user at signup — an explicit, versioned opt-in whose record outlives the session; re-consent triggers exactly when the policy version moves.
  • The user who wants their data — one button, one JSON, everything (L6); no ticket, no wait.
  • The user who leaves — a deletion that actually deletes, guarded by a word they must type, honest about errors (R8: never swallow).
  • The allergic user reading labels — told plainly which values a machine authored and where the human-curated safety sources are.
  • Whoever prices legal risk — D149 (no counsel) and the two open founder legal-basis decisions are on the record, not implied away.

Flows

  • consent ★ → GET /consent (required?) + POST /consent (append a row at the server's version); pre-household by design; the setup gate (auth) reads this ledger. (assured: test_consent, 3 api cases; the D148 gate's 27-file test migration proved the enforcement side)
  • read-the-rules → /legal/privacidad + /legal/terminos public (logged-out reachable); in-content LegalDocumentSheet inside setup + Settings so reading never drops wizard state. (assured: the legal journey, 3 e2e cases; proof set legal L1-L3)
  • disclose → Fuentes de información: pinned AI disclaimer + curated source list + legal buttons; rendered live in the profile Settings surface. (assured: the settings-disclosure journey, 1 e2e case; proof set settings-disclosure D1)
  • export → GET /account/export (setup required): one JSON attachment, version-stamped, deletion-mirrored scope incl. consent_records; web triggers the download via apiFetchBlob ("Descargar datos", AppFrame.tsx:79). (assured: test_account_export, 2 api cases) The serializer walks each row's mapped columns THROUGH THE MAPPER, not by column name: P5b's Location.order maps to the DB column display_order, and the previous getattr(obj, column.name) raised on it — taking the whole bundle down with a 500 rather than dropping one field (assured: C8122).
  • erase → DELETE /me behind the type-to-confirm gate: recipes-with-children first, no-FK sweeps, household-if-last-member, user cascade; commit, then Firebase best-effort; the web signs out and navigates. (assured: test_account_deletion 6 api + accountDeletionModel 11 web cases + the account-delete journey, 2 e2e cases)

Is

  • Append-only by construction: no consent row is ever updated or deleted while the user exists; history IS the audit trail (it leaves only inside the erasure cascade, exported first if asked).
  • Server-versioned: the accepted version is the server's constant at write time — version skew is impossible to record.
  • Export mirrors deletion: one serializer walks the same ownership graph the eraser walks (minus binary photo blobs, stated in the docstring).
  • The confirm word is locale-true: "ELIMINAR" (es) / "DELETE" (en), exact, trimmed, case-sensitive; prefix and lowercase attempts fail closed.
  • Failure copy is honest (R8): a string ApiError detail surfaces; anything else gets the generic line — never a silent success.
  • not a per-field-tolerant export — one unreadable column fails the WHOLE bundle, by construction. That is the safer default for a data-rights artifact (a silently partial export is worse than a loud failure), but it means any future column-name override is a total outage of the download until it is fixed.

Is Not

  • not the enforcement gate — auth's complete_setup raises ConsentRequiredError; this entity is the ledger it consults.
  • not legal advice — D149 explicitly shipped founder-authored documents without counsel review; the RoPA scaffold (docs/legal/DATA-INVENTORY.md) is decision-free until the two founder legal-basis calls land.
  • not analytics consent — PostHog rides legitimate-interest (L5, key-gated, PII-free); no cookie-banner machinery exists or is pretended.
  • not a retention policy — nothing ages out consent rows or exports; deletion is user-initiated only.
