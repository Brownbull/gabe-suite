Frontend placement — three ways to draw the web layer

The archmap now maps the frontend (screens + their fetches). Where do screens live on the graph? Same toy entity — Pantry, endpoints on the circle edge, models inside — drawn three ways. The dashed orange wire is a fetch bridge (screen → the endpoint it calls).

1 · Concentric ringyour approach 1

The circle you have becomes the backend. Endpoints on the edge are the entry points; anything beyond is frontend, on a faint entity-tinted band one ring out.
reads as a physical stack: request enters the edge, UI orbits outside.
keeps a screen next to the exact endpoint it calls.
a screen that fetches many entities' endpoints must pick one ring (or duplicate).

2 · Dedicated frontend entityyour approach 2

The frontend is its own entity circle, screens inside it. Bridges cross the gap to whichever backend endpoints they call.
honest when the frontend is a real separate deployable (its own repo/app).
every screen lives in ONE place, no ring-duplication.
breaks the "which entity owns this UI" reading — all screens pile in one blob.
long bridges criss-cross to every backend entity → wire spaghetti.

3 · Layer lanesmy option — reuses the lab's "Layers"

The levels lab already has a Layers view. Frontend is just the top web lane; the request falls web → api → models. Entities become colored columns.
already built (the lab's Layers level) — least new machinery.
the request path is a literal top-to-bottom fall; great for a journey walk.
loses the entity-as-a-place circle you liked; entities become columns.

4 · Satellitesmy option

No ring, no lane. Each screen is a small node tethered by its bridge wire to the exact endpoint it calls, floating just outside the edge next to that endpoint.
every screen sits ON the endpoint it calls — zero ambiguity about what it fetches.
no new container; screens are just extra nodes, cheapest render.
a busy entity (32 endpoints) gets a cloud of satellites — crowded.
a screen fetching 5 endpoints becomes 5 satellites (or one with 5 wires).
Note: option 3 · layer lanes is deferred — it becomes the separate “codebase archive in layers” view later, not this graph. Current lean: 2 · dedicated frontend entity (cleanest to read); satellites (4) is the lightest alternative.
